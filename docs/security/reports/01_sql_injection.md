# SQL Injection / Query Safety Audit

## Summary
- Files scanned: 33 (32 Python modules + 1 SQL script; `backend/models.py` consulted for table/column sensitivity)
- Findings: 5 (Critical: 0, High: 2, Medium: 2, Low: 1)
- Status: **ISSUES FOUND**

**Headline:** no classic SQL injection exists in the hand-written query layer. Every one of the 23 f-string `text(f"...")` sites interpolates either a module-level SQL constant or a locally-built static fragment, and every user-supplied value travels as a named bind parameter. All five findings sit in the **AI NL→SQL lane** (the one place where query *text* is untrusted) and in one unescaped `ILIKE` pattern.

---

## Findings

### Finding #1 — AI safety gate's forbidden-table check is bypassable with schema-qualified names
- **Severity:** High
- **File:** `backend/api/ai/safety.py`
- **Line(s):** 39-40, 90-92
- **Category:** Incomplete denylist in an SQL-text validator (regex anchored to bare table names)
- **Evidence:**

  The gate matches a forbidden table only when the name follows `from`/`join`/`into`/`update` **immediately**:

  ```python
  FORBIDDEN_TABLES = ("users", "pending_users", "auth_sessions", "refresh_sessions")  # auth/PII

  _TABLE_PATTERN = re.compile(
      r"(?ix)\b(?:from|join|into|update)\s+[\"']?(" + "|".join(FORBIDDEN_TABLES) + r")\b")
  ```

  Verified empirically against the live module (read-only, no DB access):

  ```
  (False, 'Reads from `users` are not allowed...')  <- SELECT * FROM users
  (True,  '')                                       <- SELECT * FROM public.users
  (True,  '')                                       <- SELECT * FROM ONLY users
  (True,  '')                                       <- SELECT * FROM  public . users
  (True,  '')                                       <- WITH u AS (SELECT * FROM public.users) SELECT * FROM u
  (True,  '')                                       <- SELECT * FROM public.refresh_sessions
  ```

  **Source of the interpolated/checked value:** the SQL text is generated by the local Ollama coder model from `body.question` — i.e. **attacker-influenceable free text** submitted to `POST /ai/nl-search` (`backend/api/ai/router.py:440`, `require_level(3)`) or the NL fallback lane of `POST /ai/query` (`router.py:469`, reached only when `site_scope(user) is None and user["level"] >= 3`). Exploitation means steering the LLM into emitting a schema-qualified name, not injecting SQL directly.
- **Why it's a risk:** the first wall of the documented two-wall design silently fails open for `public.users`, `public.refresh_sessions`, and `ONLY users`; only the PostgreSQL `REVOKE` in `create_ai_readonly_role.sql` then stands between an LLM-generated query and password hashes / refresh-token rows — and that REVOKE is documented as being wiped by every mirror reload (see Finding #3).
- **Suggested fix (do NOT apply):** stop pattern-matching table names in raw text. Either (a) match on an optional schema qualifier and `ONLY`/whitespace variants (`(?:only\s+)?(?:"?\w+"?\s*\.\s*)?`) as a stopgap, or (b) preferably parse the statement (e.g. `sqlglot`) and walk the resolved table set, rejecting on the parsed identifiers rather than a regex over text.
- **Effort:** Medium

### Finding #2 — Sensitive tables are readable by the AI read-only role and absent from both walls
- **Severity:** High
- **File:** `backend/scripts/create_ai_readonly_role.sql` (and `backend/api/ai/safety.py:32`)
- **Line(s):** `create_ai_readonly_role.sql` 32-37; `safety.py` 32
- **Category:** Over-broad grant / denylist omission — PII and audit data reachable by LLM-generated SELECTs
- **Evidence:**

  ```sql
  GRANT SELECT ON ALL TABLES IN SCHEMA public TO gi_ai_ro;
  ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO gi_ai_ro;

  -- Defense-in-depth: the safety gate already blocks these table names in SQL
  -- text; revoking makes the sensitive surfaces unreadable even on a bypass.
  REVOKE SELECT ON users, pending_users, auth_sessions, refresh_sessions, ai_jobs FROM gi_ai_ro;
  ```

  ```python
  FORBIDDEN_TABLES = ("users", "pending_users", "auth_sessions", "refresh_sessions")  # auth/PII
  ```

  Tables that exist in `backend/models.py`, hold personal or security-relevant data, and appear in **neither** list — so a plain query passes the gate *and* the role can read it (gate results verified: `SELECT * FROM phone_otp` → `(True, '')`, same for `employees`, `whatsapp_outbox`):

  | Table | Model line | Sensitive content |
  |---|---|---|
  | `phone_otp` | 703 | username, `new_number`, OTP timing/attempts (code itself is bcrypt-hashed) |
  | `employees` / `mh_employees` | 112 / 868 | `ID_Number`, `Name`, `Phone_Number`, department |
  | `whatsapp_outbox` | 651 | outbound message bodies + recipient phone numbers |
  | `email_outbox` | 676 | outbound email bodies + recipients |
  | `app_notifications` / `pending_summary_notifications` | 1165 / 722 | per-user notification content |
  | `system_audit_log` | 1332 | full actor/action audit trail |
  | `entry_attachments` / `mtc_documents` | 125 / 206 | BLOB-authoritative uploaded documents |
  | `bug_reports` | 1290 | triage notes, rollback/safety constraints |

  **Source:** as Finding #1 — the query text originates from LLM generation over user-supplied `question` text. Note also the asymmetry: `ai_jobs` is REVOKEd but missing from `FORBIDDEN_TABLES`.
- **Why it's a risk:** any logistics-level (level 3) account — not just admin — can ask the NL lane for data it has no UI route to, exfiltrating staff phone numbers, WhatsApp/email message contents, and the audit log; the `entry_attachments` BLOB surface additionally invites a memory/DoS-shaped response.
- **Suggested fix (do NOT apply):** invert the model — `REVOKE SELECT ON ALL TABLES`, drop the `ALTER DEFAULT PRIVILEGES` blanket grant, and `GRANT SELECT` only on the specific ERP tables/views the `SCHEMA_HINT` actually advertises. Keep `FORBIDDEN_TABLES` in sync as the text-level echo of that allowlist.
- **Effort:** Medium

### Finding #3 — Read-only role is deny-list based and fails open on new tables and after every mirror reload
- **Severity:** Medium
- **File:** `backend/scripts/create_ai_readonly_role.sql`
- **Line(s):** 32-37
- **Category:** Fail-open privilege model / unverified security control
- **Evidence:**

  ```sql
  GRANT SELECT ON ALL TABLES IN SCHEMA public TO gi_ai_ro;
  ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO gi_ai_ro;
  ...
  REVOKE SELECT ON users, pending_users, auth_sessions, refresh_sessions, ai_jobs FROM gi_ai_ro;
  ```

  **Source:** static SQL — no user input. Two structural consequences:
  1. `ALTER DEFAULT PRIVILEGES … GRANT SELECT` means **every future table** created in `public` (including the next sensitive one an alembic migration adds) is automatically readable by the AI role unless someone remembers to extend the REVOKE line.
  2. The project's own documentation states the REVOKEs are wiped by every `dual_ci`/cutover reload and must be manually re-applied (`docs/ARCHITECTURE.md` §1, `PROJECT_STATUS.md` §4). Nothing in the application verifies at startup or request time that the second wall is actually in place — with the REVOKE missing, Finding #1 becomes directly exploitable against `users`.
- **Why it's a risk:** the security control most relied upon as "defense in depth" is applied by manual operator ritual, has no runtime assertion, and defaults to granting access to anything added later.
- **Suggested fix (do NOT apply):** allowlist grants (per Finding #2), and add a cheap startup/health assertion that the AI role cannot read `users` (attempt a `SELECT 1 FROM users LIMIT 1` on the RO engine and require it to fail) so a wiped REVOKE surfaces as a red gate instead of silence.
- **Effort:** Low (the assertion) / Medium (the grant inversion)
- **Verification gap:** whether the REVOKE is presently applied on the live mirror or on production could not be checked — the audit rules prohibit touching the database. Recommend the operator confirm before relying on this wall.

### Finding #4 — User-supplied search text is used in `ILIKE` without escaping wildcards
- **Severity:** Medium
- **File:** `backend/api/stock.py`
- **Line(s):** 195-203 (pattern built at 202; consumed by `/stock/live`, `/stock/by-site`, `/stock/lots`, `/stock/expiring`)
- **Category:** Unescaped `LIKE`/`ILIKE` metacharacters — query-of-death / performance DoS (not injection)
- **Evidence:**

  ```python
  cols = ['sub."SAP_Code" ILIKE :q']
  if '"Lot_Number"' in spec["sql"]:
      cols.append('sub."Lot_Number" ILIKE :q')
  cols.append('sub."SAP_Code" IN (SELECT TRIM(i."SAP_Code") FROM inventory i '
              'WHERE i."Equipment_Description" ILIKE :q OR i."Category" ILIKE :q)')
  filters.append("(" + " OR ".join(cols) + ")")
  params["q"] = f"%{q.strip()}%"
  ```

  **Source of the interpolated value:** `q` is a request **query-string parameter** (`q: Optional[str] = Query(None, max_length=120)`, `stock.py:222` and siblings), reachable by any authenticated user. It is correctly passed as a bind parameter — the issue is the value's *content*, not its placement. A `q` of `%_%_%_%_%_%_%` forces repeated backtracking `ILIKE` scans across the derived stock view joined to `inventory`, four columns per row.
- **Why it's a risk:** cheap unauthenticated-shaped resource exhaustion from any logged-in role; the 120-char cap bounds the pattern but not the scan cost. Also a correctness papercut — a literal `%` in a SAP code can never be searched.
- **Suggested fix (do NOT apply):** escape `%`, `_` and `\` in `q` before wrapping (`q.replace('\\','\\\\').replace('%','\\%').replace('_','\\_')`) and add `ESCAPE '\'` to the `ILIKE` clauses; consider a trigram index or a minimum term length if search latency matters.
- **Effort:** Low

### Finding #5 — Configuration-introspection functions pass the safety gate
- **Severity:** Low
- **File:** `backend/api/ai/safety.py`
- **Line(s):** 42, 94-95
- **Category:** Information disclosure via allowed built-in functions
- **Evidence:**

  ```python
  _CATALOG_PATTERN = re.compile(r"(?i)\b(?:pg_\w+|information_schema)\b")
  ```

  The catalog block correctly rejects `pg_*` (verified: `SELECT pg_sleep(10)` → rejected), but functions not carrying the `pg_` prefix are untouched — verified: `SELECT current_setting('is_superuser')` → `(True, '')`. Others in this class include `current_user`, `session_user`, `version()`, `inet_server_addr()`.

  **Source:** LLM-generated text from user question input, as Findings #1/#2.
- **Why it's a risk:** minor environment/configuration disclosure to a level-3 user; no write or data-access consequence given `default_transaction_read_only` and the role's privileges.
- **Suggested fix (do NOT apply):** extend the blocked-function pattern to a small denylist (`current_setting`, `set_config`, `inet_server_*`, `version`, `current_user`, `session_user`), or move to allowlisting expressions once the parser change in Finding #1 lands.
- **Effort:** Low

## Tooling Recommendation

None of the following are present in `backend/requirements.txt`, `requirements.txt`, or `frontend/package.json`, so **nothing was installed or run**:

- **`bandit`** — specifically rule **`B608 hardcoded_sql_expressions`**, which flags string-built SQL (f-strings, `%`, `.format()`, concatenation). Against this codebase it would raise on all ~43 f-string SQL sites catalogued above; that is a high false-positive rate here, but it is exactly the tripwire that would catch a *future* site where the interpolated value is user-controlled rather than a module constant. Run it with a baseline (`bandit -b baseline.json`) so today's reviewed-clean sites stay quiet and only new ones surface. `B609`/`B611` are also worth enabling.
- **`semgrep`** with the **`p/sqlalchemy`** and **`p/python`** rulesets — `p/sqlalchemy` understands `text()` versus bound parameters and is far better than bandit at distinguishing "f-string containing a constant" from "f-string containing a request value", so it would cut most of the noise above. `p/python` adds the general injection/taint rules. Neither ruleset covers the two real problem areas found here (the regex denylist in `safety.py` and the SQL-grant model), so static analysis complements but does not replace this review.
- **`pip-audit`** — not directly SQL-related; noted here only because dependency CVEs in SQLAlchemy/asyncpg would land in this area. Recommended for the secrets/dependency pass.
